# prometheus web UI (v0)

A browser app for prometheus and its agents, for one person or a team.

- `router.ts` is the server the browser talks to: it checks who is calling, finds their folder, and forwards to a worker, starting it on first use and stopping it after 15 idle minutes (never while it works).
- `worker.ts` is one agent: a Pi SDK session in one folder (prometheus, or one agent), served as an [AG-UI](https://docs.ag-ui.com) endpoint on a unix socket only the router reaches. One process per user and agent, so each has its own session and `.env`.
- `web/` is an [assistant-ui](https://www.assistant-ui.com/docs/runtimes/ag-ui) app (Next.js) that talks to the router.

From the repository root (one `package.json` for the whole repo):

```sh
npm install
npm run ui:server     # the router, http://127.0.0.1:8787   (DEBUG=1 logs every Pi event)
npm run ui:web        # in a second terminal
```

Open the link `ui:server` prints, `http://localhost:3000/?token=…`. The page keeps the token for that tab and sends it with every request; without it the server answers 403. A restart makes a new token, so open the new link (or set `PROMETHEUS_TOKEN` to keep one).

**Who can call the server:** only the web app's origin (`UI_ORIGIN`, default `http://localhost:3000`), only at a loopback host name (`localhost`, `127.0.0.1`), and only with the token. So a page on another site can't drive the agent from your browser (origin), nor can a site re-pointed at 127.0.0.1 (host), and another program on the machine doesn't know the token. There are no logins yet: this is for one person on their own machine.

If the page says it can't reach the agent server while `ui:server` is running, and your browser runs outside WSL, start it with `HOST=0.0.0.0 npm run ui:server`: the server listens only on `127.0.0.1` by default, because it has no authentication.

Needs Node 26 or later (it runs `router.ts` and `worker.ts` directly) and the same Pi setup as the terminal: your model, your saved trust for this folder, and the globally installed packages (pi-subagents, ask-user-question). The router and workers run the global Pi itself (`npm install -g @earendil-works/pi-coding-agent`), found with `npm root -g` and loaded by path, so the page always runs the same Pi as your terminal; `PI_PACKAGE_ROOT` points at another install.

The page has three columns:

- **Left: prometheus, agents and conversations.** Headings in the title's font and size (*Agents*, *Conversations*), and under them rows as Cowork's sidebar (dark grey text, black on a grey background on hover and a darker one for the agent and conversation open, no bold; icons only on the actions at the top; every button shows the hand cursor): what is a row can be clicked, a heading can't. At the top, the title *prometheus* (the app's name, in its own colour: firebrick, `--brand` in `globals.css`, lighter in dark mode; a heading, not clickable, like the sections'), then prometheus's own rows, since it is where agents are planned, not one of them: *Forge* opens its chat, where agents are created (the planner; the chat header calls it Forge), and its commands: *New agent* opens a fresh conversation with prometheus with `/agent-new ` in the composer, and, only when an agent's copy of the skill is out of date, *Update agents* (with how many) puts `/agent-refresh --all` there (it updates only those) (the list of agents is the section below, and the Forge's *My agents* chip); Then the agents, a row each: its name, and on the right only what calls for attention, as dots explained on hover (blue, pulsing: running; violet: waits for you; amber: its copy of the skill is out of date, which *Update agents* fixes), and a › chevron that opens its actions as rows under it (and closes them): *Status* sends `/agent-status` in that agent's own chat; *Export…* goes to prometheus's chat, since it works on the folder from outside (`/agent-export <slug> `, to finish with a destination). A command that only reads is sent, once the conversation it goes to has loaded (sent during its first sync, its output never reached the page); one that changes files waits in the composer. They go to the conversation with prometheus that is open, else its latest (from `GET /agents`, i.e. `list_agents.py`, not the model; refreshed every 15 s), then the selected agent's conversations, titled by the command they began with (the worker records it), else their first message. The chat's header shows the same mark: the flame for prometheus, the agent icon for an agent.
- **Middle: the chat.** Above the input, the chat's commands as small chips: in an agent *Run* and *Status* (sent) and *Revise* and *Improve* (put in the input, to add the change or a focus; *Improve* starts a long model session, so a stray click doesn't launch it), in the Forge *My agents* (sent; a new agent is the sidebar's, which starts a fresh Forge conversation from any chat); a chip sent while the agent works waits for its turn to end (`command-bar.tsx`). What the agent did on the way folds away, as Cowork does: each stretch of steps between the things for you (a card, a reply) is one fold, so the timeline holds (the steps before a wave's line fold above it, the steps after it below). A fold reads *Working on it* while it is the agent's current stretch (with the step under way beneath it), then *Thought process*. Opened, it lists the stretch's steps in order, across the messages the agent wrote; thoughts the model kept private, and the agent's record-keeping around a wave (writing its launch and end into `run.yaml`, checking on it, closing its mission: the wave's line says all of it), are left out; a finished stretch of only one or two steps is not folded, its steps show as plain lines: its thinking as plain grey text, and each tool call as a step in words ("Reading plan.yaml", "Preparing the next wave"; the tool's name on hover; a click shows the call and its result). Below the fold come the cards that are for you (a question to answer, a panel, the agent it created, a launched wave or the plan critic) and then the answer. A launch is one plain live line ("Working on wave w1 · 3 subagents · in progress 1m 20s", then "Wave w1 · … · $0.004") that opens to one row per subagent, as Claude Code shows its own: step and agent, tool uses, tokens, time, cost, and while it works a `└` line with its latest tool call; a stage that ran its reviewed program as a command (the `batcher` runner, no model) is counted and shown as a *program*, not a subagent: its script, whether the gate passed, its time; opening it shows the command, its output and the gate's. A row opens that subagent's work in the drawer, read like the main agent's, with the same lines: its task (folded), its thoughts (a summary's **title** as a title; private ones left out), each tool call as a step in words opening to the call and its result, then the text it ended with as its answer (the `acceptance-report` block pi-subagents asks for there drawn as a card: each criterion met or not with its evidence, files changed, commands run, checks, findings, risks, notes), from its own Pi session (a command runner shows its command, output and gate). In the chat, a row with a › chevron opens; a row without one is information. An answered question is a step in the fold, "You answered: Start fresh, Same input ›", opening to each question and its answer; a question that waits for you is a card outside the fold. A thought the model sent encrypted (OpenAI's models through OpenRouter often do) shows as a note saying so, or as its readable summary when the provider sent one. The workspace's Steps stay a plain list (an icon per step); a running step names its subagents in one quiet line under it (✓ done, ✗ failed), each opening its log. Routes: `GET /…/wave?id=<subagent run id>` and `GET /…/wave/child?id=<child run id>`, read from pi-subagents' own records, only for runs inside that agent's folder. Those live in the temp folder, which macOS empties on a restart; then a wave is read from its launch in `runs/<id>/run.yaml` and each subagent from its artifacts in the folder's `.pi/sessions/subagent-artifacts/` (meta, transcript, a command's output), so an old wave still opens. Your messages after the last `/agent-…` command can be edited (the pencil on hover): Pi's session is a tree, so *Update* first rewinds it to just before that message (`POST /…/edit`, Pi's `navigateTree`, as `/tree` does in the terminal), then sends the new text, which the agent continues from; the old path stays in the session as a branch. The command and what precedes it can't be edited, since rewinding the conversation would not undo the runs and commits an agent command made; the worker enforces the same rule, and refuses while the agent works. The history the page shows is the session's current branch, each message with its Pi entry id. Replies can't be regenerated. A command shows as you typed it (`/agent-run`), not as the prompt it sends the model: the worker records which command each prompt came from in Pi's session (a custom entry the model never sees).
- **Right: the workspace** of the selected agent (with prometheus selected, the agent being planned; none, an overview of what waits for you and recent runs). *Steps* are the plan's stages, ticked as the active run finishes them (with no run active, all empty, and a line above names the last run, its status and when); while a run is active the page re-reads that one agent (`GET /a/<slug>/summary`) every 2 s, and a line above the list says what the run is doing now (the running steps, or that it waits for your approval or review, or is adjusting the plan); running steps are tinted with an accent bar, the next wave's steps say "up next"; a running step shows how many of its subagents have finished (from pi-subagents' record of the wave); *Output* is each of the last five runs as a folder (record, results, working files), read-only, with how long it took and what it cost in grey at the row's end (the agent's own model, from its sessions, plus its subagents; the split on hover) and its status only when it isn't done; the latest run's results (`runs/<id>/outputs/`) show right under it; *Input*, at the bottom, is a small file explorer of what shapes a run (`plan.yaml`, the agent role, `scripts/`, `gates/`, subagents, and `improvements.yaml`, the record `/agent-improve` keeps of what it proposed and what you decided), which you can edit (a pencil marks each file, and each folder, you can edit) in a CodeMirror editor (Save or Ctrl/Cmd-S), except the files prometheus keeps in the agent, which a refresh rewrites from `templates/agent/` (the role, `plan-critic.md`, `batcher.md`), and `improvements.yaml`, a record: those are read-only, with a small lock that says why on hover; a file you only read, and every code block in the chat and in a subagent's answer, is read-only CodeMirror without line numbers. Once the agent has run, a save opens or continues a `revise/<date>-<n>` branch (`agent_git.py begin-change`), so `main` still changes only by a reviewed merge; a banner then offers *Review and merge*, which hands the branch to `/agent-revise` (the critic, if the plan changed, then your choice). Before the first run it edits on `main`, as planning does. A run being active refuses the save. A *Changes* section lists the files that differ from `main` (click one for its diff: side by side, `main`'s copy left and the current one right, unchanged stretches folded, `@codemirror/merge`; the bin discards that file's edits) and each branch awaiting review with *Discard branch*; an open file shows the branch and has File / Changes tabs and *Discard edits*. Routes: `GET /a/<slug>/changes`, `GET /a/<slug>/diff?path=` (`{before, after}`: the file on `main`, or `HEAD` on `main`, and now; `null` where it doesn't exist), `POST /a/<slug>/discard?path=`, `POST /a/<slug>/discard-branch?name=` (the checked-out branch goes through `agent_git.py merge --action discard`), `POST /a/<slug>/checkout?name=` (a kept branch, from a clean `main`, so *Review and merge* can hand it to the agent). Discarding refuses while a run is active, since a wave's writer children are checked against the repo's staged index. The branch checked out in the agent shows beside its name (violet when it is not `main`). Clicking a file, a tool chip in the chat or *Terminal* opens it in a drawer over the workspace, with a back button, and the column widens to about 60% of the screen while it is open (the chat narrows); something new from the agent opens it too.

**One person or a team:**

| Setting | Effect |
|---|---|
| (none) | One person: you are `DEV_USER` (your login name), your folder is this repository, and you need the token. |
| `USERS_ROOT=/data/users` | Each user's folder is `USERS_ROOT/<user>/prometheus`, their own copy (agents inside it). A user without one gets 403. |
| `TRUST_USER_HEADER=x-forwarded-user` | The user comes from that header, set by a login proxy in front (e.g. oauth2-proxy with your team's identity provider); no token then. Keep the router on loopback so only the proxy reaches it, and set `UI_ORIGIN` and `ALLOWED_HOSTS` to the public address. |
| `IDLE_MINUTES` | When idle workers stop (default 15). |

**Adding a user:** `USERS_ROOT=/data/users ui/add-user.sh alice` creates `alice/{prometheus, pi-agent, files, home}`: her own clone of this repository (with its `.venv`), her Pi state with your settings and model key, a folder for her input files, and a home. `--update` pulls this repository's latest commit into her copy.

**Sandboxes** (bubblewrap, on by default when `bwrap` is installed): every worker runs in its own, and sees only what it needs, at the same paths as outside.

| | prometheus (planner) | an agent |
|---|---|---|
| prometheus's code | read-only | not there |
| `agents/` | read-write (creates, refreshes), every `.env` reads as empty | only its own folder, read-write, with its `.env` |
| your Pi state, input files (`files/` or `SANDBOX_READ`) | sessions and settings read-write; files read-only | the same |
| the rest of your home, other users | not there | not there |

The network is open (the model, an agent's connectors). With a systemd user session, each worker also gets `MEMORY_MAX` (4G) and `CPU_QUOTA` (200%); WSL usually has none. `SANDBOX=off` turns sandboxes off (development only). To see what a sandbox can do: `node ui/router.ts sandbox-run <user> p -- <command>` (or `a/<slug>` for an agent).

Routes: `GET /me`, `GET /agents` (your agents, from `list_agents.py`), `/p/…` (prometheus's agent: `agent`, `status`, `commands`) and `/a/<slug>/…` (that agent's).

How it maps:

- Pi's text, thinking and tool calls stream as AG-UI text, reasoning and tool-call events.
- An extension dialog (`ask_user_question`, select, confirm, input) ends the run with an AG-UI interrupt. The page shows it above the composer, and your answer resumes the run.
- **Panels:** the worker tells extensions it is a terminal (`mode: "tui"`), so commands with a panel of their own (`/ccstyle`, `/goal…`, `/subagents…`) open it: `ctx.ui.custom()` gets the extension's component with a minimal stand-in for Pi's TUI (its size, `requestRender`), and each frame is the component's own `render(width)`, sent whole (as [pi-web](https://github.com/agegr/pi-web) does); the chat shows it as a live card, inline where the command was typed (not in the drawer). pi-tui's standard widgets (`SettingsList`, `SelectList`, `Input`) are hijacked in the worker (their `render` records them), so a frame also carries their state and the card draws native controls (switches, segmented buttons, dropdowns, option buttons, text fields) that act through the widgets' own methods (`/…/panel/<id>/action`); other components show as styled text, (a `pi_panel` tool call; `/…/panel/<id>/stream`, `input`, `resize`) that takes keys until the extension closes it. `ask_user_question` is the exception: its panel is declined, so it falls back to its dialogs, which the chat shows as a question card. Pi's own built-in commands belong to its interactive app, not to extensions, so the worker does the useful ones itself with the SDK, and the page offers them as buttons too: `/model` (a searchable picker on the canvas; also the model name in the status bar), `/thinking` (also the status bar's dropdown), `/compact [instructions]` (also the Compact button by the context meter), `/session`, `/name` and `/reload` (also the ⋯ menu over the chat); `/new` and `/resume` point to the Conversations list. Changes apply to the conversation only, not to Pi's defaults. Credentials and machine settings (`/login`, `/settings`, …) stay with the terminal.
- Extension messages (such as `/agent-list` output) and notifications appear as assistant text.
- **History and background work.** A run that brings no new message (none, or only ones the server sent) is a *sync*: the worker answers with the conversation so far as an AG-UI messages snapshot, from Pi's own session; if the agent is working on its own (a wave finished, say), it adds what the reply in progress says so far and streams the rest until the agent settles. The page syncs when it opens, and whenever the status bar sees the agent busy without a run of its own. A page that goes away mid-run (reload, closed tab) doesn't stop the agent; the next sync picks it up.
- A worker continues the folder's latest Pi session (as `pi --continue`), so a restart (idle stop, router restart) keeps the conversation. That is also the session the terminal's `pi --continue` would pick.

Known limits: the model key in each user's `pi-agent` is readable by their agents; the network inside sandboxes is not restricted; all users' workers run as the OS user that runs the router (one Linux user per person would add a second wall). **Switching agents:** the left column lists prometheus and your agents; clicking one points the chat at that agent (`/p` or `/a/<slug>`), which loads its history, its status and its commands, and shows its state in the chat's header. The choice is kept in the address (`#/a/emails-to-excel`), so a reload stays on it. **Conversations** are the agent's Pi sessions, kept in its folder (`.pi/sessions`, the `sessionDir` of its `.pi/settings.json`), the same ones `pi --resume` lists there. Each runs in a worker of its own (`/…/s/<id>/…`; `new-…` starts one; no id is the latest); the list on the left is `GET /…/sessions`, newest first, titled by the name set with `/name`, else the command it began with, else its first message; the pencil on hover (or a double-click) renames one in place, as `/name` would (`POST /…/sessions/<id>/name`, through its worker when it is open, so the line lands on the live session's tree), and `DELETE /…/sessions/<id>` removes one for good (refused while its agent works). The planner's sandbox sees its own `.pi/sessions` read-write and every agent's as empty.

**Files:** each user has a files folder (`USERS_ROOT/<user>/files`; for one person `~/.prometheus-sandbox/files`), mounted read-only in every sandbox. The chat's **+** (or dropping files anywhere on the chat) uploads into the agent's own `uploads/` folder (made when the agent is created or refreshed, and kept out of its git; in the planner's chat, into `chat-uploads/` in your files folder) and the message carries the file's path (`PUT`/`DELETE /a/<slug>/upload?path=`), so the agent can read it and a run can be given it; removing the attachment before sending deletes it; a name already taken gets " (2)" added. An older agent keeps `uploads/` out of git through `.git/info/exclude` until a refresh adds it to its `.gitignore`. Attached files also list under *Uploaded files* in the workspace once there is one (read-only, with thumbnails for images and a small x that deletes the file). In the workspace, files you may edit (*Input*) carry a pencil, and every file and folder has its VS Code icon (the Material Icon Theme, MIT, served by the web app at `/file-icon?name=` from the theme's own manifest). An agent's workspace shows its runs and its plan, scripts, gates and subagents as folders to open: click a file to read it, or download it; `.env*`, `.git`, `.venv`, `node_modules`, `.DS_Store`, `.gitkeep` and `.pi/sessions` are never shown or served. Routes: `GET /files?dir=`, `PUT /files?path=` (the body is the file, at most `MAX_UPLOAD_MB`, 200), `DELETE /files?path=`, `GET /files/download?path=`, `GET /a/<slug>/outputs`, `GET /a/<slug>/tree?dir=`, `GET /a/<slug>/file?path=` (text up to 200 kB), `PUT /a/<slug>/file?path=` (an existing editable file, at most 1 MB), `GET /a/<slug>/download?path=`. Paths are checked to stay inside, symlinks included.

**Terminal:** the *Terminal* button over the chat opens `pi` itself on the canvas, in a real terminal in that agent's sandbox: for what only the terminal does (`/ccstyle`, `/model`, panels). It is its own Pi session, not the chat's. `pty_relay.py` (standard library, so no native module to build) runs it in a pseudo-terminal; output reaches the page as an event stream (`/…/term/stream`), keys and resizes as POSTs (`/…/term/input`, `/…/term/resize`). A page that reconnects sees the last 256 kB; pi stops a minute after the last page closes.

In the history, a command shows as you typed it.
