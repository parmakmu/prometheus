# prometheus web UI (v0)

A browser app for prometheus and its agents, for one person or a team.

- `router.ts` is the server the browser talks to: it checks who is calling, finds their folder, and forwards to a worker, starting it on first use and stopping it after 15 idle minutes (never while it works).
  The server is split by concern, each file importing what it uses: `common.ts` (settings, who is calling, the user's folders), `sandbox.ts` (what a sandbox sees, the agent's code read-only, running commands in one), `bwrap.ts` and `podman.ts` (running it with bubblewrap, or with Podman and the internet allow-list), `workers.ts` (starting, forwarding, the history before a worker is up, restarts, idle stop), `files.ts` (files, chat attachments, outputs, an agent's folder and its changes), `subagents.ts` (a wave's children as the page shows them); `router.ts` keeps the routes, terminals and conversations, and starts the server. `history.ts` builds a conversation from a session file, for the worker and the router alike.
- `worker.ts` is one agent: a Pi SDK session in one folder (prometheus, or one agent), served as an [AG-UI](https://docs.ag-ui.com) endpoint on a unix socket only the router reaches. One process per user and agent, so each has its own session and `.env`.
- `web/` is an [assistant-ui](https://www.assistant-ui.com/docs/runtimes/ag-ui) app (Next.js) that talks to the router.

From the repository root (one `package.json` for the whole repo):

```sh
npm install
npm run ui:server     # the router, http://127.0.0.1:8787   (DEBUG=1 logs every Pi event)
npm run ui:web        # in a second terminal
```

Open the link `ui:server` prints, `http://localhost:3000/?token=…`. The page keeps the token for that tab and sends it with every request; without it the server answers 403. A restart makes a new token, so open the new link (or set `PROMETHEUS_TOKEN` to keep one).

**Who can call the server:** only the web app's origin (`UI_ORIGIN`, default `http://localhost:3000`), only at a loopback host name (`localhost`, `127.0.0.1`), and only with the token. So a page on another site can't drive the agent from your browser (origin), nor can a site re-pointed at 127.0.0.1 (host), and another program on the machine doesn't know the token. There are no logins yet: this is for one person on their own machine.

If the page says it can't reach the agent server while `ui:server` is running, and your browser runs outside WSL, start it with `HOST=0.0.0.0 npm run ui:server`: the server listens only on `127.0.0.1` by default, because it has no authentication.

Needs Node 26 or later (it runs `router.ts` and `worker.ts` directly) and the same Pi setup as the terminal: your model, your saved trust for this folder, and the globally installed packages (pi-subagents, ask-user-question). The router and workers run the global Pi itself (`npm install -g @earendil-works/pi-coding-agent`), found with `npm root -g` and loaded by path, so the page always runs the same Pi as your terminal; `PI_PACKAGE_ROOT` points at another install.

The page has three columns:

In the chat, a row with a › chevron opens; a row without one is information. Routes: `GET /…/wave?id=<subagent run id>` and `GET /…/wave/child?id=<child run id>`, read from pi-subagents' own records, only for runs inside that agent's folder. Your messages after the last `/agent-…` command can be edited (the pencil on hover): Pi's session is a tree, so *Update* first rewinds it to just before that message (`POST /…/edit`, Pi's `navigateTree`, as `/tree` does in the terminal), then sends the new text, which the agent continues from; the old path stays in the session as a branch. The command and what precedes it can't be edited, since rewinding the conversation would not undo the runs and commits an agent command made; the worker enforces the same rule, and refuses while the agent works. The history the page shows is the session's current branch, each message with its Pi entry id. Replies can't be regenerated. A command shows as you typed it (`/agent-run`), not as the prompt it sends the model: the worker records which command each prompt came from in Pi's session (a custom entry the model never sees).

a file you only read, and every code block in the chat and in a subagent's answer, is read-only CodeMirror without line numbers. Once the agent has run, a save opens or continues a `revise/<date>-<n>` branch (`agent_repo.py begin-change`), so `main` still changes only by a reviewed merge; a banner then offers *Review and merge*, which hands the branch to `/agent-revise` (the critic, if the plan changed, then your choice). Before the first run it edits on `main`, as planning does. A run being active refuses the save. A *Changes* section lists the files that differ from `main` (click one for its diff: side by side, `main`'s copy left and the current one right, unchanged stretches folded, `@codemirror/merge`; the bin discards that file's edits) and each branch awaiting review with *Discard branch*; an open file shows the branch and has File / Changes tabs and *Discard edits*. Routes: `GET /a/<slug>/changes`, `GET /a/<slug>/diff?path=` (`{before, after}`: the file on `main`, or `HEAD` on `main`, and now; `null` where it doesn't exist), `POST /a/<slug>/discard?path=`, `POST /a/<slug>/discard-branch?name=` (the checked-out branch goes through `agent_repo.py merge --action discard`), `POST /a/<slug>/checkout?name=` (a kept branch, from a clean `main`, so *Review and merge* can hand it to the agent). Discarding refuses while a run is active, since a wave's writer children are checked against the repo's staged index. The branch checked out in the agent shows beside its name (violet when it is not `main`). Clicking a file, a tool chip in the chat or *Terminal* opens it in a drawer over the workspace, with a back button, and the column widens to about 60% of the screen while it is open (the chat narrows); something new from the agent opens it too.

**One person or a team:**

| Setting | Effect |
|---|---|
| (none) | One person: you are `DEV_USER` (your login name), your folder is this repository, and you need the token. |
| `USERS_ROOT=/data/users` | Each user's folder is `USERS_ROOT/<user>/prometheus`, their own copy (agents inside it). A user without one gets 403. |
| `TRUST_USER_HEADER=x-forwarded-user` | The user comes from that header, set by a login proxy in front (e.g. oauth2-proxy with your team's identity provider); no token then. Keep the router on loopback so only the proxy reaches it, and set `UI_ORIGIN` and `ALLOWED_HOSTS` to the public address. It needs `PROXY_SECRET` too (16+ characters), which the proxy sends in `x-proxy-secret` (or `PROXY_SECRET_HEADER`): sandboxes share the router's network, so without it an agent could call the router as anyone. The router refuses to start without it. |
| `IDLE_MINUTES` | When idle workers stop (default 15). |

**Adding a user:** `USERS_ROOT=/data/users ui/add-user.sh alice` creates `alice/{prometheus, pi-agent, files, home}`: her own clone of this repository (with its `.venv`), her Pi state with your settings and model key, a folder for her input files, and a home. `--update` pulls this repository's latest commit into her copy.

**Sandboxes** (`SANDBOX`: `bwrap`, the default when bubblewrap is installed; `podman`; or `off`, for development only): every worker runs in its own, and sees only what it needs, at the same paths as outside. Both backends get the same mounts (one description, run by either), and the escape tests in `tests/test_router.py` run against each one installed.

- **`bwrap`** (one person, your machine): starts in about 10 ms. Memory and CPU limits only with a systemd user session, which WSL usually lacks.
- **`podman`** (a team server): a rootless container per worker (`sudo apt install podman`). It adds memory and CPU limits wherever your cgroups allow them (`MEMORY_MAX`, `CPU_QUOTA`), a loopback of its own (an agent can't reach the router's port), no capabilities, and a process limit. With [gVisor](https://gvisor.dev) installed, `PODMAN_RUNTIME=runsc` (or its path) puts its user-space kernel between the agent and yours; the router passes it `ignore-cgroups`, which a normal user needs, and refuses to start if the runtime can't start a container. Under WSL with Ubuntu's runsc (2023), it couldn't: install a current release from gvisor.dev. Each start costs about half a second. Containers a crashed router left are removed at the next start.
- **The internet, by allow-list** (`podman` only; `EGRESS=off` turns it off): workers sit on an internal network with no route out. The only way out is `ui/egress_proxy.py`, a small HTTPS proxy the router runs in a container on that network and an outbound one. It lets each agent reach the base hosts (model providers and PyPI; `EGRESS_BASE` replaces the list) plus the hosts you allowed for that agent, which are kept in your folder (`<your folder>/network/<agent>.json`), outside every sandbox. An agent proves who it is with a token in its `HTTPS_PROXY`, and Node honours that through `NODE_USE_ENV_PROXY=1`; a tool that ignores the proxy has no way out at all. The workspace's **Internet** section shows what the agent may reach, and offers the hosts its plan asks for (`network:`) and the ones it was refused, each with an Allow button (`GET`/`POST /a/<slug>/network`).

| | prometheus (planner) | an agent |
|---|---|---|
| prometheus's code | read-only | not there |
| `agents/` | read-write (creates, refreshes), every `.env` reads as empty | only its own folder, read-write, with its `.env`; but its code read-only: `.pi/` (extensions, skills, settings, subagent profiles; not `sessions/`, `subagents/`, `npm/`, `APPEND_SYSTEM.md`) and `.git/config`, `.git/hooks` |
| your Pi state (`~/.pi/agent`) | read-only, except what Pi and pi-subagents write while running (`sessions/`, `missions/`, `pi-subagents/`, `tmp/`, `auth.json`, logs); `settings.json` is a copy per user, so a change made in the web app stays there | the same |
| input files (`files/` or `SANDBOX_READ`) | read-only | the same |
| the rest of your home, other users | not there | not there |

With bubblewrap the network is open (the model, an agent's connectors); with Podman it's by allow-list (above). With a systemd user session, each worker also gets `MEMORY_MAX` (4G) and `CPU_QUOTA` (200%); WSL usually has none. `SANDBOX=off` turns sandboxes off (development only). To see what a sandbox can do: `node ui/router.ts sandbox-run <user> p -- <command>` (or `a/<slug>` for an agent).

**How a sandbox is built** (for contributors). Every process the router starts for a user or an agent (its Pi worker, the terminal, the router's own git and script calls on its folder) goes through one function, `sandboxed()` in `sandbox.ts`. Its `describe()` says what the sandbox sees, whatever runs it: a list of mounts (read-only, writable, or an empty tmpfs), the environment and the working folder (a `Spec`). The backend `SANDBOX` names turns that into a command: `bwrap.ts` into `bwrap … -- <command>` (adding the `/bin` links, `/proc`, `/dev`, WSL's resolver file and systemd's limits), `podman.ts` into `podman run` (adding everything below). So there is one description of a sandbox, and the escape tests in `tests/test_router.py` run against each backend installed.

- **No image.** The container's root is an empty folder the router prepares (mount points, and links like `bin → usr/bin` as Ubuntu has), passed as `--rootfs <folder>:O`; the overlay (`:O`) lets Podman add its own mount points without changing it, and the folder comes last, right before the command, since `--rootfs` is a switch whose folder takes the image's place. Into it go the parts of your machine the table above lists, at the same paths as outside (`/usr`, `/etc`, node, Pi, your Pi state, the agent's folder, your files), so a path in a session or a run record means the same inside and out. The one exception is WSL's resolver file, which bubblewrap needs and Podman doesn't: it has its own DNS, which knows the proxy's name.
- **Who it runs as.** Podman runs rootless, as you, with no daemon. `--userns=keep-id` makes the process inside uid 1000, as you are outside, so what it writes is yours. Every container also gets `--cap-drop=all`, `--security-opt=no-new-privileges` and `--pids-limit=2048`, plus `--memory`/`--cpus` when your cgroups delegate those controllers (WSL doesn't, so they're left off).
- **Talking to it.** No ports: a worker listens on a socket file in a small folder of its own, mounted into its container, and the router connects to that file from outside.
- **Start and stop.** The router runs `podman run --rm --init …` as a child process; `--init` passes signals to the worker, and `--rm` deletes the container when it stops. Every container is labelled `prometheus.router=<the router's pid>`: on exit the router removes its own, and on start those whose router is gone (after a crash). A start costs about half a second, against about 10 ms for bubblewrap.
- **The network.** Two Podman networks are created once per user: `prometheus-<uid>-internal` (`--internal`: no route out) and `prometheus-<uid>-out`. Every sandbox joins only the internal one, so a direct connection fails. The egress proxy, `egress_proxy.py` in a container built the same way, joins both. Each sandbox's `HTTPS_PROXY` names the proxy with a token for its user and agent (`NODE_USE_ENV_PROXY=1` makes Node's `fetch` use it). The proxy looks the token up in `allow.json`, which the router writes into a folder shared with the proxy, and refused hosts go to `refused.jsonl` in the same folder.
- **gVisor.** `PODMAN_RUNTIME=runsc` passes `--runtime runsc --runtime-flag ignore-cgroups` to Podman; at start the router checks that the runtime starts a container, and stops if it can't.
- **To look inside:** `SANDBOX=podman node ui/router.ts sandbox-run <user> a/<slug> -- sh` opens a shell in that agent's container.


Routes: `GET /me`, `GET /agents` (your agents, from `agent_list.py`), `/p/…` (prometheus's agent: `agent`, `status`, `commands`) and `/a/<slug>/…` (that agent's, and its `params`). Scripts the router runs itself, outside the sandbox, are always prometheus's copy, never the agent's: the agent's model can write its own folder.

How it maps:

- Pi's text, thinking and tool calls stream as AG-UI text, reasoning and tool-call events.
- An extension dialog (`ask_user_question`, select, confirm, input) ends the run with an AG-UI interrupt. The page shows it above the composer, and your answer resumes the run.
- **Panels:** the worker tells extensions it is a terminal (`mode: "tui"`), so commands with a panel of their own (`/ccstyle`, `/goal…`, `/subagents…`) open it: `ctx.ui.custom()` gets the extension's component with a minimal stand-in for Pi's TUI (its size, `requestRender`), and each frame is the component's own `render(width)`, sent whole (as [pi-web](https://github.com/agegr/pi-web) does); the chat shows it as a live card, inline where the command was typed (not in the drawer). pi-tui's standard widgets (`SettingsList`, `SelectList`, `Input`) are hijacked in the worker (their `render` records them), so a frame also carries their state and the card draws native controls (switches, segmented buttons, dropdowns, option buttons, text fields) that act through the widgets' own methods (`/…/panel/<id>/action`); other components show as styled text, (a `pi_panel` tool call; `/…/panel/<id>/stream`, `input`, `resize`) that takes keys until the extension closes it. `ask_user_question` is the exception: its panel is declined, so it falls back to its dialogs, which the chat shows as a question card. Pi's own built-in commands belong to its interactive app, not to extensions, so the worker does the useful ones itself with the SDK, and the page offers them as buttons too: `/model` (a searchable picker on the canvas; also the model name in the status bar), `/thinking` (also the status bar's dropdown), `/compact [instructions]` (also the Compact button by the context meter), `/session`, `/name` and `/reload` (also the ⋯ menu over the chat); `/new` and `/resume` point to the Conversations list. Changes apply to the conversation only, not to Pi's defaults. Credentials and machine settings (`/login`, `/settings`, …) stay with the terminal.
- Extension messages (such as `/agent-list` output) and notifications appear as assistant text.
- **History and background work.** A run that brings no new message (none, or only ones the server sent) is a *sync*: the worker answers with the conversation so far as an AG-UI messages snapshot, from Pi's own session; if the agent is working on its own (a wave finished, say), it adds what the reply in progress says so far and streams the rest until the agent settles. The page syncs when it opens, and whenever the status bar sees the agent busy without a run of its own. A page that goes away mid-run (reload, closed tab) doesn't stop the agent; the next sync picks it up.
- A worker continues the folder's latest Pi session (as `pi --continue`), so a restart (idle stop, router restart) keeps the conversation. That is also the session the terminal's `pi --continue` would pick.
- **Opening a conversation fast.** A worker takes about 2 s to start, most of it loading Pi, so the router answers the page's first sync itself, from the session file (`ui/history.ts`, the snapshot the worker builds too; about 30 ms), and the page sends that sync at once. Until it is answered the chat shows a loading skeleton, not a new chat's welcome; until the worker itself answers (its first status), the input and the command chips are grayed out, with "Starting pi…" as the placeholder. Pointing at an agent in the sidebar starts its worker, workers keep Node's compile cache in the sandbox's home, and a worker whose agent was refreshed restarts as soon as it is idle with no run active (Pi loads an extension only when a session starts).

Known limits: the model key in each user's `pi-agent` is readable by their agents; the network inside sandboxes is not restricted; all users' workers run as the OS user that runs the router (one Linux user per person would add a second wall). **Switching agents:** the left column lists prometheus and your agents; clicking one points the chat at that agent (`/p` or `/a/<slug>`), which loads its history, its status and its commands, and shows its state in the chat's header. The choice is kept in the address (`#/a/emails-to-excel`), so a reload stays on it. **Conversations** are the agent's Pi sessions, kept in its folder (`.pi/sessions`, the `sessionDir` of its `.pi/settings.json`), the same ones `pi --resume` lists there. Each runs in a worker of its own (`/…/s/<id>/…`; `new-…` starts one; no id is the latest); the list on the left is `GET /…/sessions`, newest first, titled by the name set with `/name`, else the command it began with, else its first message; the pencil on hover (or a double-click) renames one in place, as `/name` would (`POST /…/sessions/<id>/name`, through its worker when it is open, so the line lands on the live session's tree), and `DELETE /…/sessions/<id>` removes one for good (refused while its agent works). The planner's sandbox sees its own `.pi/sessions` read-write and every agent's as empty.

**Files:** each user has a files folder (`USERS_ROOT/<user>/files`; for one person `~/.prometheus-sandbox/files`), mounted read-only in every sandbox. The chat's **+** (or dropping files anywhere on the chat) uploads the file: in an agent's chat into your files folder under the agent's name (`files/<slug>/`), so it outlives runs and prunes and a path to it in `.env` keeps working; in the planner's chat into prometheus's `inputs/` (out of git; of prometheus's folder the page sees only `inputs/`). The message carries the file's path (`PUT`/`DELETE /a/<slug>/upload?path=`, `/p/upload?path=`), so the agent can read it and a run can be given it; removing the attachment before sending deletes it; a name already taken gets " (2)" added. Agents have no folder of their own for attachments: a refresh removes an older agent's empty `uploads/`, and keeps one with files, out of git, until you move them. Attached files also list under *Uploaded files* in the workspace once there is one (read-only, with thumbnails for images and a small x that deletes the file). In the workspace, files you may edit (*Input*) carry a pencil, and every file and folder has its VS Code icon (the Material Icon Theme, MIT, served by the web app at `/file-icon?name=` from the theme's own manifest). An agent's workspace shows its runs and its plan, scripts, gates and subagents as folders to open: click a file to read it, or download it; `.env*`, `.git`, `.venv`, `node_modules`, `.DS_Store`, `.gitkeep`, `.pi/sessions` and `.plan` (the planner's record of how the plan was made) are never shown or served. Routes: `GET /files?dir=`, `PUT /files?path=` (the body is the file, at most `MAX_UPLOAD_MB`, 200), `DELETE /files?path=`, `GET /files/download?path=`, `GET /a/<slug>/outputs`, `GET /a/<slug>/tree?dir=`, `GET /a/<slug>/file?path=` (text up to 200 kB), `PUT /a/<slug>/file?path=` (an existing editable file, at most 1 MB), `GET /a/<slug>/download?path=`. Paths are checked to stay inside, symlinks included.

> Replaced by `prometheus serve` (a release over HTTP and A2A, one agent per process; see `docs/how-to.md`, "How to serve an agent over HTTP"). The run API stays while the web app is in use, but gets no new features.

**The run API** (`api.ts`): an agent called like a service, on its own, by a script or another agent. Each call is one run of that agent, in its sandbox, in a session of its own (listed with its sessions, titled by the request, with an *API* tag), driven by `/agent-auto`. Where the run needs someone (a question, an approval, a review, or the model asking in words) the call waits in `needs_input` until the caller answers: the question goes back to whoever called. An agent has one active run, so calls to it run one at a time and the rest queue (also behind a run started from its chat). Routes, under `/a/<slug>/api`:

| | |
|---|---|
| `GET /` | the agent: request, goal, `done_when`, params (name, type, required, whether set here; never values), inputs, outputs, the stages that ask for approval or a review (`plan_edit.py card`) |
| `POST /runs` | `{request, params?, files?, approve?, max_cost_usd?}` → 202 `{id}`. `params`: values for this run only, over the agent's `.env` (never secrets, which stay set on the agent); a relative path resolves inside the run. `files`: `{path: base64}`, put in the run's `inputs/` (so `{"mail_dir": "inputs/emails"}`). `approve`: stage keys, or `true` for all. Checked against the card first: a plan that isn't ready is 409 |
| `GET /runs`, `GET /runs/<id>` | the calls: `status` (`queued`, `running`, `needs_input`, `done`, `failed`, `cancelled`), `run`, `session`, `question` (`kind`, `message`, `options`), and at the end `report` (the agent's last words), `outputs` (files in the run's `outputs/`), `cost_usd` and `cost` (`agent`: the model that drove the run, in the call's own session; `subagents`: the run's children) |
| `GET /runs/<id>/events` | server-sent events: `status` on every change, and the AG-UI events the page would get |
| `POST /runs/<id>/answer` | `{answer}`: the option, the text, or a reply to the model's words |
| `GET /runs/<id>/outputs/<path>` | an output file |
| `DELETE /runs/<id>` | cancel: a queued call is dropped; a running one stops its worker and its run (a wave still out keeps the run active; the call says so) |

Who may call: you (the web app's token or login), or a key for that agent: `Authorization: Bearer pak.…`, made with `POST /a/<slug>/api-keys {label}` (the key is shown once; only its hash is kept, in `<your folder>/api-keys.json`), listed with `GET` and revoked with `DELETE ?id=`. A key opens that agent's API and nothing else: not the page, not another agent, not the keys. Calls are kept in `<your folder>/api/<slug>/`, outside every sandbox. A router that stops loses the calls it was driving: they are marked failed (their run stays, to continue in the web app); queued ones go on when the agent's API is next called.

**Terminal:** the *Terminal* button over the chat opens `pi` itself on the canvas, in a real terminal in that agent's sandbox: for what only the terminal does (`/ccstyle`, `/model`, panels). It is its own Pi session, not the chat's. `pty_relay.py` (standard library, so no native module to build) runs it in a pseudo-terminal; output reaches the page as an event stream (`/…/term/stream`), keys and resizes as POSTs (`/…/term/input`, `/…/term/resize`). A page that reconnects sees the last 256 kB; pi stops a minute after the last page closes.

In the history, a command shows as you typed it.
